# forge — спецификация v0.1

> Рабочее название `forge`. Статус: черновик, 2026-11-18.
> Личный плагин Claude Code для любого проекта. Замена Superpowers.

## 1. Цель и принципы

**Цель.** Дать Claude Code дисциплину процесса (план → исполнение → проверка → ревью), не тратя лимиты подписки на церемонии и не уговаривая модель капслоком.

**Принципы**

1. **Механика вместо уговоров.** Всё, что должно происходить всегда или никогда, делают хуки и CLI. Скиллы — только там, где нужно суждение.
2. **Строгость по размеру задачи.** Опечатка не проходит через спеку и план. Рискованная правка не проходит без ревью.
3. **Лимиты — главный ресурс.** Основная сессия держит чистый контекст: чтение и поиск уходят дешёвым субагентам, которые возвращают выжимку. Модель и effort выбираются по роли, а не «по умолчанию».
4. **Не переизобретать Claude Code.** Plan mode, worktrees, список задач, Workflow, субагенты, хуки уже есть. forge — это политика поверх них, а не замена.
5. **Тихо по умолчанию.** Никакого манифеста в каждую сессию. Старт сессии добавляет в контекст не больше 5 строк.
6. **Измеримо.** Изменения в скиллах и таблице моделей проверяются набором задач (evals), а не ощущением.
7. **Fail-open, кроме охраны.** Ошибка внутри плагина не блокирует работу: хук пишет в лог и выходит с 0. Исключение — охранные хуки `pre-bash` и `pre-edit`: при внутренней ошибке они отвечают `ask` (fail-closed), иначе сбой охраны молча разрешал бы всё.
8. **Язык пользователя.** Всё, что forge показывает, — на английском или русском, по языку, на котором пишет пользователь (профиль `language` и `FORGE_LANG` закрепляют язык). Сообщения живут в каталогах модулей `{ en, ru }`, паритет проверяет тест; логи, скиллы и агенты — по-английски.

**Не цели:** публичный фреймворк для всех; поддержка других агентов (Codex и т.п.); замена CI; командные процессы.

## 2. Термины

| Термин | Значение |
|---|---|
| Профиль | `.forge/profile.json` в проекте: команды проверки, защищённые ветки и файлы, рискованные пути, режим. Коммитится (по желанию) |
| Состояние | `.forge/state.json`: уровень задачи, стадия, результаты проверки, счётчики неудач. Не коммитится |
| Уровень (tier) | T0–T3, насколько строгий процесс нужен задаче |
| Стадия | `spec → plan → execute → review → finish` |
| Роль | Субагент с фиксированными инструментами и записью в таблице маршрутизации |
| Режим | `eco / normal / max` — сдвигает таблицу моделей вниз или вверх |

## 3. Архитектура

```
┌──────────────── Claude Code ────────────────┐
│ основная сессия (модель выбирает пользователь)
│   │ вызывает                                │
│   ├── скиллы forge:*  ── читают ──┐         │
│   ├── субагенты (роли) ◄── model/effort ── forge route
│   └── Bash: forge <cmd>           │         │
│                                   ▼         │
│ хуки ── читают/пишут ──► .forge/profile.json, state.json
└─────────────────────────────────────────────┘
```

- **Хуки** — инварианты: охрана, автопроверка, учёт правок, короткий контекст.
- **CLI `forge`** — единая точка логики (профиль, состояние, маршрутизация, проверка). Хуки и скиллы вызывают одну и ту же библиотеку `lib/`, поэтому логика тестируется юнит-тестами.
- **Скиллы** — стадии процесса, где нужно суждение.
- **Роли-субагенты** — исполнители с фиксированными инструментами; модель и effort подставляются при вызове.

### Структура репозитория

Целевая структура. В 0.2.0 нет агентов `mechanic` и `architect` (их роли исполняют `implementer` и основная сессия), скиллов `debug` и `finish` и каталога `evals/`; остальное существует.

```
forge/
├── .claude-plugin/
│   ├── plugin.json
│   └── marketplace.json      # репозиторий сам себе маркетплейс
├── hooks/
│   ├── hooks.json
│   └── *.mjs                 # тонкие обёртки над lib/
├── agents/                   # scout, mechanic, implementer, architect, reviewer, debugger
├── skills/                   # init, mode, plan, execute, review, docs, release, debug, finish
├── bin/forge                 # CLI, на PATH пока плагин включён
├── lib/                      # profile, state, route, verify, guards, detect, docs, changelog, release
├── config/
│   ├── routing.json          # таблица маршрутизации по режимам
│   └── profile.schema.json   # JSON Schema профиля (автодополнение в редакторе)
├── evals/
├── test/
└── docs/spec.md
```

## 4. Уровни задач

| Уровень | Примеры | Процесс |
|---|---|---|
| **T0** — тривиально | вопрос, опечатка, переименование | Ничего, кроме охранных хуков |
| **T1** — малая правка | баг в 1–3 файлах, понятная правка | Правка → автопроверка при завершении. **Уровень по умолчанию** |
| **T2** — фича | новая функциональность, несколько модулей | Короткая спека → план → исполнение ролями → ревью → проверка |
| **T3** — рискованно | миграции БД, auth, деньги, публичный API, CI, удаление данных | Как T2 + ревью обязательно + явное «да» пользователя перед необратимым |

**Кто определяет уровень.** В хуках нет LLM-классификации — это было бы и дорого, и ненадёжно.

- По умолчанию действует T1.
- T2 включается, когда Claude или пользователь запускает `forge:plan`. Скилл пишет уровень в состояние.
- T3 в 0.2.0 выбирает скилл `forge:plan` (если файлы задачи попадают под `risky_paths`); хуки уровни не проверяют и правки не блокируют. Механическая блокировка по `risky_paths` — в планах (§13, «Дальше»).
- Пользователь может задать уровень вручную: `/forge:plan` или `forge state set tier N`.

## 5. Профиль проекта

`.forge/profile.json`. Формат JSON выбран вместо YAML: парсер не нужен (ноль зависимостей), а JSON Schema даёт автодополнение и проверку в редакторе.

```json
{
  "$schema": "https://…/forge/profile.schema.json",
  "version": 1,
  "commands": {
    "format": "npx prettier --write {files}",
    "lint": "npx eslint {files}",
    "typecheck": "npx tsc --noEmit",
    "test": "npm test",
    "test_fast": "npm test -- --onlyChanged"
  },
  "verify": {
    "steps": ["typecheck", "lint", "test"],
    "on_stop": "fast",
    "timeout_sec": 300
  },
  "git": {
    "protected_branches": ["main", "master", "release/*"]
  },
  "protected_files": [".env*", "**/*.pem", "secrets/**"],
  "risky_paths": ["**/migrations/**", "**/auth/**", ".github/workflows/**"],
  "docs": { "remind": true, "max_lines": 200, "watch": [] },
  "release": { "changelog": "CHANGELOG.md", "tag_prefix": "v", "version_files": ["package.json"] },
  "tdd": "encouraged",
  "mode": "normal",
  "routing": {}
}
```

- `{files}` подставляется списком изменённых файлов.
- `verify.on_stop`: `fast` (берёт `test_fast`, если задан), `full`, `off`. Для проектов с долгими тестами (iOS) по умолчанию `off` + только lint.
- `docs` (с 0.3.0): `remind` — напоминание в конце хода (по умолчанию `true`); `max_lines` — предел длины агентского файла для `forge docs` (по умолчанию 200); `watch` дописывается к встроенному списку файлов, изменение которых требует проверить агентские файлы (`package.json`, `pyproject.toml`, `Cargo.toml`, `*.sln`, `Makefile`, `justfile`, `Taskfile.yml`, `docker-compose*.yml`, `compose*.yml`, `.github/workflows/**`, `.gitlab-ci.yml`); `!шаблон` снимает.
- `release` (с 0.4.0, включается по желанию): без раздела выпуски и напоминание выключены, `{}` включает со значениями по умолчанию. `changelog` — путь к журналу в формате Keep a Changelog (`CHANGELOG.md`); `tag_prefix` — префикс тега версии (`v`); `version_files` — файлы с версией: строка-путь (обработчик по имени: `*.json` — `version` верхнего уровня, `pyproject.toml` — `[project]` или `[tool.poetry]`, `Cargo.toml` — `[package]`, `pom.xml` — собственная `<version>` проекта, `*.csproj` — `<Version>`) или `{ "path", "pattern" }` с регулярным выражением ровно с одной группой захвата (по умолчанию `[]`); `remind` — напоминание про пустой `[Unreleased]` (`true`); `ignore` дописывается к встроенному списку файлов, правка которых записи не требует (`test/**`, `tests/**`, `**/__tests__/**`, `**/*.test.*`, `**/*.spec.*`, `docs/**`, `*.md`, `**/*.md`, `.forge/**`); `!шаблон` снимает.
- `tdd`: `off | encouraged | required`. Хуки его не применяют: `forge:plan` при `required` ставит тестовые задачи перед реализацией, `forge:execute` передаёт значение ролям.
- `routing` — частичное переопределение таблицы из §8.

**Автоопределение.** `forge init` смотрит на `package.json` (scripts), `pyproject.toml`, `Package.swift` / `*.xcodeproj`, `go.mod`, `Cargo.toml` и предлагает профиль. Пользователь подтверждает. В MVP поддерживаются Node/TS, Python, Swift, Go и Rust.

**Автоопределение выпусков (0.4.0).** Независимо от стека `forge init` предлагает раздел `release`, если нашёл в корне хотя бы один признак: `CHANGELOG.md`; git-теги версий (`x.y.z`, `vx.y.z`); CI, который публикует или выпускает (`docker push`, `npm publish`, `twine upload`, `cargo publish`, `dotnet nuget push`, `gh release`, `goreleaser`), запускается по тегам или вручную с параметром `publish`/`deploy`/`release`. В `version_files` попадают корневые `package.json`, `.claude-plugin/plugin.json`, `pyproject.toml`, `Cargo.toml`, `pom.xml`, `*.csproj` с версией не `0.0.0` и корневые `README*.md` с бейджем `version-x.y.z-`. Решение «выпускается ли проект» остаётся за пользователем: раздел только предлагается.

**Без профиля** работают только охранные хуки со встроенными значениями по умолчанию. Старт сессии пишет одну строку: «профиля нет, `/forge:init`».

**Что не коммитится.** `forge init` добавляет `.forge/state.json`, `.forge/edits.jsonl`, `.forge/work/` и `.forge/log/` в `.git/info/exclude` (а не в `.gitignore`), чтобы не трогать файлы проекта. Сам профиль коммитить или нет — решает пользователь.

## 6. Состояние

`.forge/state.json` — одно на рабочую директорию. Параллельные сессии работают в отдельных worktree, и у каждого своё состояние. Две сессии в одном checkout — известное ограничение, не поддерживается.

```json
{
  "tier": 1,
  "stage": "execute",
  "mode": "normal",
  "task": { "slug": "oauth-login", "started_at": "…" },
  "artifacts": { "spec": ".forge/work/oauth-login/spec.md", "plan": ".forge/work/oauth-login/plan.md" },
  "verify": { "at": "…", "ok": false, "summary": "test: код 1", "failed_step": "test", "edits_offset": 512, "notified": false },
  "failures": { "verify_streak": 2 },
  "lint_offset": 512,
  "docs": { "offset": 512, "reminded": { "scripts": { "package.json": "3f2a…" }, "dirs": ["tools"] } }
}
```

Состояние меняется только через `forge state …` и хуки, а не ручным редактированием JSON моделью.

**Журнал правок.** Изменённые файлы пишутся не в `state.json`, а в `.forge/edits.jsonl` — по строке на правку, только дозаписью. Так параллельные `PostToolUse`-хуки не затирают друг друга. Линт, проверка и напоминания `Stop` хранят свои смещения в журнале (`lint_offset`, `verify.edits_offset`, `docs.offset`) и берут файлы, изменённые после них; `docs.offset` — одно окно правок для напоминаний про агентские файлы и про пустой `[Unreleased]`. Когда все действующие смещения догнали конец и журнал не меньше 256 КБ, он обнуляется. Отсутствующее `docs.offset` означает «догнал» и обнуление не задерживает; когда оба напоминания выключены, `Stop` удаляет `state.docs`, чтобы старый курсор не держал обнуление. `docs.reminded` — память напоминаний (отпечаток `scripts` на каждый `package.json`, имена новых каталогов): признак, о котором уже напомнили, не повторяется, пока не изменится; запись забывается, когда признак снова совпал с `HEAD`. `release.reminded` (0.4.0) — память напоминания про выпуск: список из не более чем 20 ключей, ключ — имя ветки, а на ветке по умолчанию (`origin/HEAD`, иначе `main`/`master`) и при отсоединённом `HEAD` — `<ветка>@<последний тег версии|none>`.

## 7. Хуки

| Событие | Матчер | Что делает | Выход | Этап |
|---|---|---|---|---|
| `SessionStart` | startup, resume, clear, compact | Добавляет до 7 строк (не больше 600 символов): стек, команда проверки, режим, текущие уровень и стадия, путь к плану. Предупреждает, если включён Superpowers. С профилем добавляет строку про корневые агентские файлы: нет `AGENTS.md` или `CLAUDE.md` не подключает его (проверка двух файлов без обхода каталогов; `CLAUDE.md` — символическая ссылка на `AGENTS.md` — считается подключением). Строка про агентские файлы стоит перед строкой про Superpowers и может быть обрезана пределом 600 символов | `additionalContext` | v0.1, строка про агентские файлы — 0.3.0 |
| `PreToolUse` | `Bash` | **Запрет:** push в защищённую ветку, `push` с `--force`/`-f`/`+refspec` (даже вместе с `--force-with-lease`: `--force` перекрывает lease; одни `--force-with-lease`/`--force-if-includes` в незащищённую ветку разрешены), `--mirror`, `commit`/`push --no-verify`. **Подтверждение пользователя:** `reset --hard`, `push --all`, `rm -r` за пределами проекта или по пути из переменной. Содержимое `$(...)`, обратных кавычек, `<(...)`/`>(...)` и heredoc без кавычек у разделителя проверяется рекурсивно, как `bash -c`; общий предел вложенности 3 (`bash -c`, `eval`, подстановки), глубже, при незакрытой подстановке или входе, который разборщик не может проследить (предел вложенности и бюджет шагов), — `ask`. Разбор следует правилам bash: ANSI-C `$'…'`, склейка `\`+перевод строки, `<<-` против `<<`, арифметика `$((…))`, `case` только на месте команды; сокращённые длинные опции git читаются как полные. При внутренней ошибке охраны — `ask` (fail-closed). Известные пропуски (имя команды из подстановки, stdin-скрипты, обёртки со значением флага) — в [docs/ru/guards.md](ru/guards.md), «Ограничения»; охрана — страховка от ошибок, а не песочница | `permissionDecision: deny` или `ask` + причина | v0.1 |
| `PreToolUse` | `Edit\|Write\|MultiEdit\|NotebookEdit` | `protected_files` → запрет. При внутренней ошибке проверки — `ask` (fail-closed) | `deny` / `ask` + причина | v0.1 |
| `PreToolUse` | то же | *(не реализовано, см. §13)* `risky_paths` при уровне < T3 → запрет с подсказкой поднять уровень. Уровень ≥ T2 и нет плана → запрет «сначала план» | `deny` + причина | v0.2 |
| `PostToolUse` | `Edit\|Write\|MultiEdit\|NotebookEdit` | Дописывает файл и время правки в журнал `.forge/edits.jsonl` (`lib/edits.mjs`). Ничего не запускает | — | v0.1 |
| `PostToolBatch` | — | Один раз на пачку правок: `format` + `lint` по изменённым файлам. Ошибки передаёт Claude, ход не прерывается (`decision: block` на `PostToolBatch` останавливает цикл и показывает причину только пользователю) | `hookSpecificOutput.additionalContext` + сжатый вывод | v0.1 |
| `Stop` | — | Если правки были позже последней проверки — запускает `verify`. Падение → не даёт остановиться и показывает сжатый вывод. Отпускает только при повторной остановке (`stop_hook_active`) и серии падений ≥ 3 подряд: тогда не блокирует, а сообщает пользователю о падении | `decision: block` / `systemMessage` | v0.1 |
| `Stop` | — | Напоминание про агентские файлы (курсор `docs.offset` уходит в конец журнала после каждой остановки): если с прошлой остановки менялись файлы из `docs.watch` (`package.json` — только `scripts` против `HEAD` репозитория своего каталога, `git -C <каталог>`; вне git — любая правка) или появился каталог верхнего уровня, которого нет в `HEAD` и в корневом `AGENTS.md`, и в том же окне не правился `AGENTS.md` (или `CLAUDE.md` с содержимым) в каталоге изменения или выше, — не даёт остановиться и просит проверить, не устарели ли файлы. Память `docs.reminded` гасит повтор того же отпечатка `scripts` и того же каталога. Нет `AGENTS.md` ни в корне, ни над изменёнными файлами — молчит без вызовов git. Проверка (`verify`) важнее: при её падении или «отпускании» напоминания нет, курсор остаётся; ошибка напоминания пишется в лог и не отменяет ответ проверки. Первая остановка после обновления только заводит курсор. Выключается `docs.remind: false`; общий курсор `state.docs` удаляется, только когда выключены оба напоминания | `decision: block` | 0.3.0 |
| `Stop` | — | Напоминание про журнал изменений (0.4.0, только с разделом `release`, выключается `release.remind: false`): в том же окне правок (общий курсор `docs.offset`) менялся файл, не являющийся журналом и не подходящий под `release.ignore`, а в `[Unreleased]` нет записей — не даёт остановиться и просит добавить запись или сказать, что она не нужна. Один раз на ветку; на ветке по умолчанию и при отсоединённом `HEAD` — один раз на последний тег версии (память `release.reminded`). Нет файла журнала — молчит (его отсутствие показывает `forge release --check`). Если сработали оба напоминания, причины идут одним `block` через пустую строку; ошибка одной части пишется в лог и не стоит второй. Проверка (`verify`) важнее, как и для напоминания про агентские файлы | `decision: block` | 0.4.0 |
| `Stop` | — | *(не реализовано)* На T3: нет `review.md` новее последней правки → не даёт остановиться, просит `forge:review` | `decision: block` | v0.2 |
| `SubagentStart` | роли forge | *(не реализовано)* Даёт субагенту карточку роли и команду проверки из профиля, не раздувая основную сессию | `additionalContext` | v0.2 |

Планируемая цепочка для рискованных правок (в 0.2.0 хуками не реализована): правка в `risky_paths` блокируется → Claude поднимает уровень до T3 → на T3 нельзя завершить работу без свежего ревью.

Хуки ролей (например, «отчёт исполнителя обязан содержать раздел Evidence с командой и результатом») живут во frontmatter самих агентов (`hooks:`), а не в общем `hooks.json`.

**Нефункциональные требования**

- Каждый хук, кроме проверки, укладывается в 150 мс (p95).
- Вывод в контекст обрезается: не больше 60 строк, сначала сводка.
- При внутренней ошибке хук выходит с 0 и пишет в `.forge/log/`. `forge doctor` показывает эти ошибки. Исключение — `pre-bash` и `pre-edit`: они отвечают `ask`.
- Охранные хуки дополняют разрешения Claude Code, а не заменяют их.

Пример `hooks.json`:

```json
{
  "hooks": {
    "PreToolUse": [
      { "matcher": "Bash",
        "hooks": [{ "type": "command", "command": "node \"${CLAUDE_PLUGIN_ROOT}/hooks/pre-bash.mjs\"" }] },
      { "matcher": "Edit|Write|MultiEdit|NotebookEdit",
        "hooks": [{ "type": "command", "command": "node \"${CLAUDE_PLUGIN_ROOT}/hooks/pre-edit.mjs\"" }] }
    ],
    "Stop": [
      { "hooks": [{ "type": "command", "command": "node \"${CLAUDE_PLUGIN_ROOT}/hooks/stop.mjs\"", "timeout": 600 }] }
    ]
  }
}
```

## 8. Роли и маршрутизация моделей

### Роли

| Роль | Задача | Инструменты |
|---|---|---|
| `scout` | Поиск и чтение кода, сбор контекста, возврат выжимки | Только чтение: Read, Grep, Glob |
| `mechanic` | Правки по точной инструкции: переименования, шаблонный код, тесты по образцу | Чтение + правка, Bash |
| `implementer` | Задача из плана, где нужно думать | Чтение + правка, Bash |
| `senior` | Задача плана, которую нельзя описать до конца или где ошибка дорога; повтор после падения implementer | Чтение + правка, Bash |
| `architect` | Спека, план, разбиение на задачи | Чтение, запись только в `.forge/work/` |
| `reviewer` | Ревью диффа: баги, риски, соответствие спеке | Только чтение + Bash для тестов |
| `debugger` | Эскалация: трудный баг, повторные падения | Всё |

Поле `tools` не умеет ограничивать пути, поэтому «запись только в `.forge/work/`» у architect обеспечивает его собственный `PreToolUse`-хук во frontmatter. Bash у reviewer формально позволяет писать; это принятый риск, ревьюер получает инструкцию только запускать проверки.

### Таблица маршрутизации (`config/routing.json`)

| Роль | eco | normal | max |
|---|---|---|---|
| scout | haiku / low | haiku / low | sonnet / medium |
| mechanic | sonnet / low | sonnet / medium | sonnet / high |
| implementer | sonnet / medium | sonnet / high | opus / high |
| senior | sonnet / high | opus / high | opus / xhigh |
| architect | sonnet / high | opus / high | opus / xhigh |
| reviewer | sonnet / high | opus / high | fable / high |
| debugger | opus / high | fable / high | fable / high |

**Как это работает.** Frontmatter агента задаёт значения режима `normal` как запасной вариант (для `senior` это не так: без `model` от диспетчера задача senior пойдёт на `sonnet/high` из frontmatter implementer). Скиллы перед вызовом субагента выполняют `forge route <role>` и передают полученные `model` и `effort` в вызов. Так режим переключается одной командой (`/forge:mode eco`) без правки файлов агентов.

**Инварианты** (проверяются тестом над `routing.json` и при загрузке переопределений из профиля):

- reviewer не слабее implementer в любом режиме (сравнение по модели, затем по effort);
- senior не слабее implementer. Встроенная таблица держит senior строго сильнее (проверяет тест), а переопределения профиля могут их уравнять — тогда первый повтор просто повторяет ту же модель;
- reviewer не слабее senior;
- debugger не слабее senior — это следующая ступень лестницы повторов;
- в `eco` нет `fable`;
- scout никогда не получает инструменты записи.

**Эскалация по фактам.** `failures.verify_streak` растёт при каждом упавшем `verify` и обнуляется при успехе. На 2 подряд Stop-хук добавляет в причину: «передай задачу роли debugger с логом падений». Хук не запускает агента сам — он даёт механический сигнал, а решение принимает модель.

Для задач плана `forge:execute` строит лестницу повторов: первый повтор идёт ступенью выше с логом падения (`mechanic` → `implementer`, `implementer` → `senior`, `senior` → `senior`), второе падение передаётся `debugger` с обоими логами. Повтор той же моделью, что упала, мало что даёт; ступень выше видит то, что пропустила слабая.

**Основная сессия.** Её модель выбирает пользователь, forge её не меняет. Запуск параллельных implementer'ов с `isolation: worktree` — в планах: сейчас ни скиллы, ни хуки его не задают, параллельно идут только задачи с непересекающимися файлами.

## 9. Скиллы

| Скилл | Кто вызывает | Что делает | Артефакт |
|---|---|---|---|
| `forge:init` | пользователь | Определяет стек, создаёт профиль, настраивает exclude | `.forge/profile.json` |
| `forge:mode` | пользователь | `eco / normal / max` | состояние |
| `forge:plan` | модель (T2+) или пользователь | Уточняет задачу (короткая спека встроена), пишет план. Уровень T2/T3 | `spec.md`, `plan.md` |
| `forge:execute` | модель или пользователь | Идёт по плану: роль на задачу, независимые задачи параллельно, проверка после каждой | отметки в `plan.md` |
| `forge:review` | модель (обязательно на T3) или пользователь | Reviewer по диффу относительно базы; находки с серьёзностью | `review.md` |
| `forge:docs` | модель или пользователь | Заводит, переносит и делит агентские файлы по схеме «`AGENTS.md` — источник, рядом `CLAUDE.md` с `@AGENTS.md`»; начинает с `forge docs --json`, ничего не пишет без согласия пользователя, переносит текст дословно и сверяет, что строки не потеряны (0.3.0) | `AGENTS.md`, `CLAUDE.md` |
| `forge:release` | модель (когда пользователь просит выпустить версию) или пользователь | Проводит выпуск проекта с разделом `release`: `forge release --check`, чтение `[Unreleased]` с предложением правок формулировок, уровень вместе с пользователем, `forge release <уровень> --yes` (принятые правки журнала и файлов версий перед этим коммитятся: нужно чистое дерево); push и шаги проекта (публикация, деплой, GitHub-релиз) — только с явного согласия и только описанные в `AGENTS.md` или документации; если ничего не описано, предлагается лишь GitHub-релиз (при `gh` и GitHub-remote); отказ push из-за охраны forge не обходится: скилл предлагает отправить тег отдельно или порядок, принятый в проекте (0.4.0) | журнал, файлы версий, коммит и тег |
| `forge:debug` | модель при падениях | Воспроизвести → гипотеза → минимальный тест → исправление → проверка; эскалация на debugger | — |
| `forge:finish` | модель или пользователь | Финальная проверка, сводка, предложение коммита или PR. Никогда не пушит без «да» пользователя | — |

**Формат задачи в плане** (машиночитаемый, чтобы позже исполнять его Workflow-скриптом):

```markdown
- [ ] T3 Добавить refresh-токены
  role: implementer
  files: src/auth/token.ts, src/auth/token.spec.ts
  check: npm test -- token.spec
  depends: T1
```

**Правила написания скиллов**

- `description` начинается с «Use …» (Use to…, Use before…) и называет узкий триггер. Никаких «1% шанса» и «ты обязан».
- Тело — до ~150 строк, объясняет «почему», а не только «что». Подробности — в файлах рядом, они подгружаются по требованию.
- Тяжёлая работа уходит ролям через вызов субагента с `model` и `effort` из `forge route`. `context: fork` во frontmatter скилла не используется: он фиксирует модель статически, и режимы перестали бы работать.

## 11. Технические решения

- **Node ≥ 20, ESM (`.mjs`), ноль зависимостей.** JSON родной, на macOS Node уже есть (npx используется), запуск ~40 мс.
- **Тесты:** `node:test`. Хуки тестируются подачей JSON на stdin и проверкой stdout и кода выхода на фикстурах.
- **Распространение:** свой GitHub-репозиторий с `marketplace.json` → установка через `/plugin` на любой машине. Локальная разработка — запуск Claude Code с каталогом плагина.
- **Superpowers** при включённом forge выключается. forge от него не зависит и не копирует тексты, но берёт удачные идеи (systematic debugging, обязательные доказательства при проверке).
- **Что не делаем:** не подменяем главный агент через `settings.json` плагина и не вешаем хук на `UserPromptSubmit` в MVP — это инъекции в каждый ход.

## 12. Evals

- 10–15 реальных задач из своих репозиториев, по 3–4 на каждый уровень T0–T3.
- Три конфигурации: Claude без надстроек, Superpowers, forge (режимы `normal` и `eco`).
- Метрики: задача решена (тесты зелёные), токены как прокси расхода лимита, время, число вопросов к пользователю, лишние церемонии на T0/T1, пропущенный обязательный шаг на T3.
- Запуск только при изменении скиллов или `routing.json`, а не постоянно — evals тоже тратят лимит.
- Инструмент — `claude plugin eval`. Формат набора уточнить при реализации.

## 14. Критерии готовности MVP

1. В репозитории без профиля нет шума: одна строка с подсказкой про `/forge:init`.
2. `git push origin main` блокируется с понятной причиной. `git push --force-with-lease` в свою ветку проходит.
3. После правки кода попытка завершить работу запускает проверку. Падение возвращается Claude. Повторная остановка после падения не уходит в цикл.
4. После `/forge:mode eco` следующие вызовы субагентов идут на моделях из колонки `eco` (видно в транскрипте).
5. Контекст от `SessionStart` — не больше 600 символов.
6. Хуки, кроме проверки, укладываются в 150 мс p95 на средней машине.
7. Сломанный профиль не блокирует работу: хуки работают со значениями по умолчанию, `forge doctor` показывает ошибку.

## 15. Открытые вопросы

| Вопрос | Как закрыть |
|---|---|
| Финальное название плагина | Решить до публикации репозитория |
| Формат `claude plugin eval` | Есть в CLI: кейсы `evals/**/case.yaml` или `prompt.md` + `graders/*.md`. Разобрать перед v0.2 |

**Закрыто при реализации:** `PostToolBatch` срабатывает после пачки параллельных вызовов инструментов, до следующего вызова модели; по документации хуков Claude Code `decision: block` на нём останавливает цикл и показывает причину как предупреждение, а `hookSpecificOutput.additionalContext` попадает в контекст перед следующим вызовом модели. forge 0.2.0 использует второе. передачи `effort` в вызов субагента хватает: в двух проектах владельца 40 из 40 вызовов субагентов получили model и effort из `forge route`. `SessionStart` приходит с источниками `startup`, `resume`, `clear`, `compact`, `fork`. У `Stop` есть встроенный предел — 8 продолжений подряд, сбрасывается при вызове инструмента; forge отпускает сам при повторной остановке (`stop_hook_active`) с 3-го падения подряд.
