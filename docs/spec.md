# forge — спецификация v0.1

> Рабочее название `forge`. Статус: черновик, 2026-11-18.
> Личный плагин Claude Code для любого проекта. Замена Superpowers.

## 1. Цель и принципы

**Цель.** Дать Claude Code дисциплину процесса (план → исполнение → проверка → ревью), не тратя лимиты подписки на церемонии и не уговаривая модель капслоком.

**Принципы**

1. **Механика вместо уговоров.** Всё, что должно происходить всегда или никогда, делают хуки и CLI. Скиллы — только там, где нужно суждение.
2. **Строгость по размеру задачи.** Опечатка не проходит через спеку и план. Рискованная правка не проходит без ревью.
3. **Лимиты — главный ресурс.** Основная сессия держит чистый контекст: чтение и поиск уходят дешёвым субагентам, которые возвращают выжимку. Модель и effort выбираются по роли, а не «по умолчанию».
4. **Не переизобретать Claude Code.** Plan mode, worktrees, список задач, Workflow, субагенты, хуки уже есть. forge — это политика поверх них, а не замена.
5. **Тихо по умолчанию.** Никакого манифеста в каждую сессию. Старт сессии добавляет в контекст не больше 5 строк.
6. **Измеримо.** Изменения в скиллах и таблице моделей проверяются набором задач (evals), а не ощущением.
7. **Fail-open.** Ошибка внутри плагина никогда не блокирует работу: хук пишет в лог и выходит с 0.

**Не цели:** публичный фреймворк для всех; поддержка других агентов (Codex и т.п.); замена CI; командные процессы.

## 2. Термины

| Термин | Значение |
|---|---|
| Профиль | `.forge/profile.json` в проекте: команды проверки, защищённые ветки и файлы, рискованные пути, режим. Коммитится (по желанию) |
| Состояние | `.forge/state.json`: уровень задачи, стадия, результаты проверки, счётчики неудач. Не коммитится |
| Уровень (tier) | T0–T3, насколько строгий процесс нужен задаче |
| Стадия | `spec → plan → execute → review → finish` |
| Роль | Субагент с фиксированными инструментами и записью в таблице маршрутизации |
| Режим | `eco / normal / max` — сдвигает таблицу моделей вниз или вверх |

## 3. Архитектура

```
┌──────────────── Claude Code ────────────────┐
│ основная сессия (модель выбирает пользователь)
│   │ вызывает                                │
│   ├── скиллы forge:*  ── читают ──┐         │
│   ├── субагенты (роли) ◄── model/effort ── forge route
│   └── Bash: forge <cmd>           │         │
│                                   ▼         │
│ хуки ── читают/пишут ──► .forge/profile.json, state.json
└─────────────────────────────────────────────┘
```

- **Хуки** — инварианты: охрана, автопроверка, учёт правок, короткий контекст.
- **CLI `forge`** — единая точка логики (профиль, состояние, маршрутизация, проверка). Хуки и скиллы вызывают одну и ту же библиотеку `lib/`, поэтому логика тестируется юнит-тестами.
- **Скиллы** — стадии процесса, где нужно суждение.
- **Роли-субагенты** — исполнители с фиксированными инструментами; модель и effort подставляются при вызове.

### Структура репозитория

```
forge/

├── evals/
├── test/

```

## 4. Уровни задач

| Уровень | Примеры | Процесс |
|---|---|---|
| **T0** — тривиально | вопрос, опечатка, переименование | Ничего, кроме охранных хуков |
| **T1** — малая правка | баг в 1–3 файлах, понятная правка | Правка → автопроверка при завершении. **Уровень по умолчанию** |
| **T2** — фича | новая функциональность, несколько модулей | Короткая спека → план → исполнение ролями → ревью → проверка |
| **T3** — рискованно | миграции БД, auth, деньги, публичный API, CI, удаление данных | Как T2 + ревью обязательно + явное «да» пользователя перед необратимым |

**Кто определяет уровень.** В хуках нет LLM-классификации — это было бы и дорого, и ненадёжно.

- По умолчанию действует T1.
- T2 включается, когда Claude или пользователь запускает `forge:plan`. Скилл пишет уровень в состояние.
- T3 включается **механически**: правка файла из `risky_paths` при уровне ниже T3 блокируется хуком с объяснением. Claude либо поднимает уровень (`forge state set tier 3`), либо спрашивает пользователя.
- Пользователь может задать уровень вручную: `/forge:plan` или `forge state set tier N`.

## 5. Профиль проекта

`.forge/profile.json`. Формат JSON выбран вместо YAML: парсер не нужен (ноль зависимостей), а JSON Schema даёт автодополнение и проверку в редакторе.

```json
{
  "$schema": "https://…/forge/profile.schema.json",
  "version": 1,
  "commands": {
    "format": "npx prettier --write {files}",
    "lint": "npx eslint {files}",
    "typecheck": "npx tsc --noEmit",
    "test": "npm test",
    "test_fast": "npm test -- --onlyChanged"
  },
  "verify": {
    "steps": ["typecheck", "lint", "test"],
    "on_stop": "fast",
    "timeout_sec": 300
  },
  "git": {
    "protected_branches": ["main", "master", "release/*"]
  },
  "protected_files": [".env*", "**/*.pem", "secrets/**"],
  "risky_paths": ["**/migrations/**", "**/auth/**", ".github/workflows/**"],
  "tdd": "encouraged",
  "mode": "normal",
  "routing": {}
}
```

- `{files}` подставляется списком изменённых файлов.
- `verify.on_stop`: `fast` (берёт `test_fast`, если задан), `full`, `off`. Для проектов с долгими тестами (iOS) по умолчанию `off` + только lint.
- `tdd`: `off | encouraged | required`. `required` действует только на T2+.
- `routing` — частичное переопределение таблицы из §8.

**Автоопределение.** `forge init` смотрит на `package.json` (scripts), `pyproject.toml`, `Package.swift` / `*.xcodeproj`, `go.mod`, `Cargo.toml` и предлагает профиль. Пользователь подтверждает. В MVP поддерживаются Node/TS, Python, Swift, Go и Rust.

**Без профиля** работают только охранные хуки со встроенными значениями по умолчанию. Старт сессии пишет одну строку: «профиля нет, `/forge:init`».

**Что не коммитится.** `forge init` добавляет `.forge/state.json`, `.forge/work/` и `.forge/log/` в `.git/info/exclude` (а не в `.gitignore`), чтобы не трогать файлы проекта. Сам профиль коммитить или нет — решает пользователь.

## 6. Состояние

`.forge/state.json` — одно на рабочую директорию. Параллельные сессии работают в отдельных worktree, и у каждого своё состояние. Две сессии в одном checkout — известное ограничение, не поддерживается.

```json
{
  "tier": 1,
  "stage": "execute",
  "mode": "normal",
  "task": { "slug": "oauth-login", "started_at": "…" },
  "artifacts": { "spec": ".forge/work/oauth-login/spec.md", "plan": ".forge/work/oauth-login/plan.md" },
  "verify": { "at": "…", "ok": false, "summary": "test: код 1", "failed_step": "test", "edits_offset": 512, "notified": false },
  "failures": { "verify_streak": 2 },
  "lint_offset": 512
}
```

Состояние меняется только через `forge state …` и хуки, а не ручным редактированием JSON моделью.

**Журнал правок.** Изменённые файлы пишутся не в `state.json`, а в `.forge/edits.jsonl` — по строке на правку, только дозаписью. Так параллельные `PostToolUse`-хуки не затирают друг друга. Линт и проверка хранят свои смещения в журнале (`lint_offset`, `verify.edits_offset`) и берут файлы, изменённые после них. Когда оба догнали конец и журнал больше 256 КБ, он обнуляется.

## 7. Хуки

| Событие | Матчер | Что делает | Выход | Этап |
|---|---|---|---|---|
| `SessionStart` | startup, resume, compact | Добавляет ≤5 строк: стек, команда проверки, режим, текущие уровень и стадия, путь к плану. Предупреждает, если включён Superpowers | `additionalContext` | v0.1 |
| `PreToolUse` | `Bash` | **Запрет:** push в защищённую ветку, `push --force` и `+refspec` (`--force-with-lease` в свою ветку разрешён), `--mirror`, `commit`/`push --no-verify`. **Подтверждение пользователя:** `reset --hard`, `push --all`, `rm -r` за пределами проекта или по пути из переменной | `permissionDecision: deny` или `ask` + причина | v0.1 |
| `PreToolUse` | `Edit\|Write\|MultiEdit\|NotebookEdit` | `protected_files` → запрет | `deny` + причина | v0.1 |
| `PreToolUse` | то же | `risky_paths` при уровне < T3 → запрет с подсказкой поднять уровень. Уровень ≥ T2 и нет плана → запрет «сначала план» | `deny` + причина | v0.2 |
| `PostToolUse` | `Edit\|Write\|MultiEdit` | Записывает файл и время правки в состояние. Ничего не запускает | — | v0.1 |
| `PostToolBatch` | — | Один раз на пачку правок: `format` + `lint` по изменённым файлам. Ошибки возвращает Claude | `decision: block` + сжатый вывод | v0.1 |
| `Stop` | — | Если правки были позже последней проверки — запускает `verify`. Падение → не даёт остановиться и показывает сжатый вывод. Если `stop_hook_active` и снова падение → отпускает, но требует честно сообщить пользователю о падении | `decision: block` / `additionalContext` | v0.1 |
| `Stop` | — | На T3: нет `review.md` новее последней правки → не даёт остановиться, просит `forge:review` | `decision: block` | v0.2 |
| `SubagentStart` | роли forge | Даёт субагенту карточку роли и команду проверки из профиля, не раздувая основную сессию | `additionalContext` | v0.2 |

Цепочка для рискованных правок замкнута механически: правка в `risky_paths` блокируется → Claude поднимает уровень до T3 → на T3 нельзя завершить работу без свежего ревью.

Хуки ролей (например, «отчёт исполнителя обязан содержать раздел Evidence с командой и результатом») живут во frontmatter самих агентов (`hooks:`), а не в общем `hooks.json`.

**Нефункциональные требования**

- Каждый хук, кроме проверки, укладывается в 150 мс (p95).
- Вывод в контекст обрезается: не больше 60 строк, сначала сводка.
- При внутренней ошибке хук выходит с 0 и пишет в `.forge/log/`. `forge doctor` показывает эти ошибки.
- Охранные хуки дополняют разрешения Claude Code, а не заменяют их.

Пример `hooks.json`:

```json
{
  "hooks": {
    "PreToolUse": [
      { "matcher": "Bash",
        "hooks": [{ "type": "command", "command": "node \"${CLAUDE_PLUGIN_ROOT}/hooks/pre-bash.mjs\"" }] },
      { "matcher": "Edit|Write|MultiEdit|NotebookEdit",
        "hooks": [{ "type": "command", "command": "node \"${CLAUDE_PLUGIN_ROOT}/hooks/pre-edit.mjs\"" }] }
    ],
    "Stop": [
      { "hooks": [{ "type": "command", "command": "node \"${CLAUDE_PLUGIN_ROOT}/hooks/stop.mjs\"", "timeout": 330 }] }
    ]
  }
}
```

## 8. Роли и маршрутизация моделей

### Роли

| Роль | Задача | Инструменты |
|---|---|---|
| `scout` | Поиск и чтение кода, сбор контекста, возврат выжимки | Только чтение: Read, Grep, Glob |
| `mechanic` | Правки по точной инструкции: переименования, шаблонный код, тесты по образцу | Чтение + правка, Bash |
| `implementer` | Задача из плана, где нужно думать | Чтение + правка, Bash |
| `architect` | Спека, план, разбиение на задачи | Чтение, запись только в `.forge/work/` |
| `reviewer` | Ревью диффа: баги, риски, соответствие спеке | Только чтение + Bash для тестов |
| `debugger` | Эскалация: трудный баг, повторные падения | Всё |

Поле `tools` не умеет ограничивать пути, поэтому «запись только в `.forge/work/`» у architect обеспечивает его собственный `PreToolUse`-хук во frontmatter. Bash у reviewer формально позволяет писать; это принятый риск, ревьюер получает инструкцию только запускать проверки.

### Таблица маршрутизации (`config/routing.json`)

| Роль | eco | normal | max |
|---|---|---|---|
| scout | haiku / low | haiku / low | sonnet / medium |
| mechanic | sonnet / low | sonnet / medium | sonnet / high |
| implementer | sonnet / medium | sonnet / high | opus / high |
| architect | sonnet / high | opus / high | opus / xhigh |
| reviewer | sonnet / high | opus / high | fable / high |
| debugger | opus / high | fable / high | fable / high |

**Как это работает.** Frontmatter агента задаёт значения режима `normal` как запасной вариант. Скиллы перед вызовом субагента выполняют `forge route <role>` и передают полученные `model` и `effort` в вызов. Так режим переключается одной командой (`/forge:mode eco`) без правки файлов агентов.

**Инварианты** (проверяются тестом над `routing.json` и при загрузке переопределений из профиля):

- reviewer не слабее implementer в любом режиме (сравнение по модели, затем по effort);
- в `eco` нет `fable`;
- scout никогда не получает инструменты записи.

**Эскалация по фактам.** `failures.verify_streak` растёт при каждом упавшем `verify` и обнуляется при успехе. На 2 подряд Stop-хук добавляет в причину: «передай задачу роли debugger с логом падений». Хук не запускает агента сам — он даёт механический сигнал, а решение принимает модель.

**Основная сессия.** Её модель выбирает пользователь, forge её не меняет. Параллельные implementer'ы запускаются с `isolation: worktree`.

## 9. Скиллы

| Скилл | Кто вызывает | Что делает | Артефакт |
|---|---|---|---|
| `forge:init` | пользователь | Определяет стек, создаёт профиль, настраивает exclude | `.forge/profile.json` |
| `forge:mode` | пользователь | `eco / normal / max` | состояние |
| `forge:plan` | модель (T2+) или пользователь | Уточняет задачу (короткая спека встроена), пишет план. Уровень T2/T3 | `spec.md`, `plan.md` |
| `forge:execute` | модель или пользователь | Идёт по плану: роль на задачу, независимые задачи параллельно, проверка после каждой | отметки в `plan.md` |
| `forge:review` | модель (обязательно на T3) или пользователь | Reviewer по диффу относительно базы; находки с серьёзностью | `review.md` |
| `forge:debug` | модель при падениях | Воспроизвести → гипотеза → минимальный тест → исправление → проверка; эскалация на debugger | — |
| `forge:finish` | модель или пользователь | Финальная проверка, сводка, предложение коммита или PR. Никогда не пушит без «да» пользователя | — |

**Формат задачи в плане** (машиночитаемый, чтобы позже исполнять его Workflow-скриптом):

```markdown
- [ ] T3 Добавить refresh-токены
  role: implementer
  files: src/auth/token.ts, src/auth/token.spec.ts
  check: npm test -- token.spec
  depends: T1
```

**Правила написания скиллов**

- `description` начинается с «Use when…» и описывает узкий триггер. Никаких «1% шанса» и «ты обязан».
- Тело — до ~150 строк, объясняет «почему», а не только «что». Подробности — в файлах рядом, они подгружаются по требованию.
- Тяжёлая работа уходит ролям через вызов субагента с `model` и `effort` из `forge route`. `context: fork` во frontmatter скилла не используется: он фиксирует модель статически, и режимы перестали бы работать.

## 10. CLI `forge`

| Команда | Назначение |
|---|---|
| `forge init [--yes]` | Автоопределение и создание профиля |
| `forge state get [key]` / `set key value` | Чтение и изменение состояния |
| `forge mode [eco\|normal\|max]` | Показать или переключить режим |
| `forge route <role>` | Вывести `model=… effort=…` для роли в текущем режиме |
| `forge verify [--fast]` | Запустить шаги проверки, записать результат, вывести сжатую сводку |
| `forge doctor` | Версия Node, валидность профиля, ошибки хуков из лога, конфликт с Superpowers |

## 11. Технические решения

- **Node ≥ 20, ESM (`.mjs`), ноль зависимостей.** JSON родной, на macOS Node уже есть (npx используется), запуск ~40 мс.
- **Тесты:** `node:test`. Хуки тестируются подачей JSON на stdin и проверкой stdout и кода выхода на фикстурах.
- **Распространение:** свой GitHub-репозиторий с `marketplace.json` → установка через `/plugin` на любой машине. Локальная разработка — запуск Claude Code с каталогом плагина.
- **Superpowers** при включённом forge выключается. forge от него не зависит и не копирует тексты, но берёт удачные идеи (systematic debugging, обязательные доказательства при проверке).
- **Что не делаем:** не подменяем главный агент через `settings.json` плагина и не вешаем хук на `UserPromptSubmit` в MVP — это инъекции в каждый ход.

## 12. Evals

- 10–15 реальных задач из своих репозиториев, по 3–4 на каждый уровень T0–T3.
- Три конфигурации: Claude без надстроек, Superpowers, forge (режимы `normal` и `eco`).
- Метрики: задача решена (тесты зелёные), токены как прокси расхода лимита, время, число вопросов к пользователю, лишние церемонии на T0/T1, пропущенный обязательный шаг на T3.
- Запуск только при изменении скиллов или `routing.json`, а не постоянно — evals тоже тратят лимит.
- Инструмент — `claude plugin eval`. Формат набора уточнить при реализации.

## 13. Этапы

**v0.1 — MVP (сделано 2026-11-18)**

- Каркас плагина, `plugin.json`, `marketplace.json`.
- CLI: `init`, `state`, `mode`, `route`, `verify`, `doctor`.
- Профиль + JSON Schema (копируется в `.forge/` при `init`) + автоопределение Node/TS, Python, Swift, Go, Rust.
- Хуки: `SessionStart`, `PreToolUse` (Bash + файлы, без логики уровней), `PostToolUse`, `PostToolBatch`, `Stop`.
- Агенты: `scout`, `implementer`, `reviewer`, `debugger`. Роль `mechanic` пока исполняет агент `implementer` со своей строкой таблицы; `architect` — основная сессия (`agent=main`).
- Скиллы: `init`, `mode`, `plan`, `execute`, `review`.
- 45 тестов (`npm test`): охрана, glob, разбор shell, маршрутизация, профиль, проверка, автоопределение, хуки и CLI end-to-end.

**v0.2**

## 14. Критерии готовности MVP

1. В репозитории без профиля нет шума: одна строка с подсказкой про `/forge:init`.
2. `git push origin main` блокируется с понятной причиной. `git push --force-with-lease` в свою ветку проходит.
3. После правки кода попытка завершить работу запускает проверку. Падение возвращается Claude. Повторная остановка после падения не уходит в цикл.
4. После `/forge:mode eco` следующие вызовы субагентов идут на моделях из колонки `eco` (видно в транскрипте).
5. Контекст от `SessionStart` — не больше 600 символов.
6. Хуки, кроме проверки, укладываются в 150 мс p95 на средней машине.
7. Сломанный профиль не блокирует работу: хуки работают со значениями по умолчанию, `forge doctor` показывает ошибку.

## 15. Открытые вопросы

| Вопрос | Как закрыть |
|---|---|
| Финальное название плагина | Решить до публикации репозитория |
| Когда именно срабатывает `PostToolBatch` в живой сессии | Валидатор 2.1.326 событие принимает; поведение проверить в первой реальной сессии. Хук не зависит от его входа — файлы берутся из журнала правок |
| Формат `claude plugin eval` | Есть в CLI: кейсы `evals/**/case.yaml` или `prompt.md` + `graders/*.md`. Разобрать перед v0.2 |
| Нужны ли `effort`-переопределения на уровне скилла или хватит передачи в вызов субагента | Решить по опыту первых недель |

**Закрыто при реализации:** `SessionStart` приходит с источниками `startup`, `resume`, `clear`, `compact`, `fork`. У `Stop` есть встроенный предел — 8 продолжений подряд, сбрасывается при вызове инструмента; forge отпускает сам уже на 3-м падении подряд.
