# CLI forge

Хуки и скиллы зовут `forge` для всего детерминированного; запускать его можно и самому — в Bash-инструменте Claude Code или, вне Claude Code, как `node /path/to/forge/bin/forge <команда>`.

## Команды

| Команда | Что делает | Код выхода |
|---|---|---|
| `forge init` | Показывает [стек](profile.md#автоопределение-стека), предлагаемый профиль и заметки; ничего не пишет | 0 |
| `forge init --work local\|docs` | Выбирает, где [`forge:plan`](skills.md#forgeplan) хранит спеки и планы: `local` — `.forge/work/` (по умолчанию), `docs` — `docs/specs/{slug}.md` и `docs/plans/{slug}.md`. Работает и с предпросмотром, и с `--yes`; без флага `init` [предлагает](profile.md#автоопределение-стека) `docs`, если есть `docs/specs/` или `docs/plans/` | 0; 2 — значение не указано или неизвестно |
| `forge init --yes [--force]` | Пишет профиль и копию схемы, добавляет [исключения](profile.md#что-пишет-init) в `.git/info/exclude`; существующий профиль перезаписывает только с `--force` | 0; 1 — профиль уже есть |
| `forge state [get [key]]` | [Состояние](state.md#файл-состояния) целиком или поле по пути через точку (`task.slug`) | 0 |
| `forge state set <key> <value> […]` | Меняет поля парами; значение читается как JSON, иначе как строка. Проверяются `tier` (целое 0–3), `stage` (`spec`, `plan`, `execute`, `review`, `finish` или `null`), `mode` | 0; 2 — ошибка |
| `forge state reset` | Сбрасывает `tier` (на 1), `stage`, `task`, `artifacts`, `failures`; режим, результат проверки и курсоры остаются | 0 |
| `forge mode [eco\|normal\|max]` | Показывает или переключает [режим](routing.md#модели-по-режимам) (в состоянии) и печатает таблицу режима | 0; 2 — неизвестный режим |
| `forge route <role> [--json]` | `role=… mode=… agent=… model=… effort=…` или то же в JSON ([как это используют скиллы](routing.md#как-скиллы-вызывают-роль)) | 0; 2 — роль не указана или неизвестна |
| `forge route --table` | Таблица текущего режима | 0 |
| `forge work <slug> [--json]` | `spec=… plan=…` или `{spec, plan}` в JSON: пути из поля [`work`](profile.md#поля-профиля) профиля с подставленными `{slug}` и `{date}` | 0; 2 — slug не указан или не в kebab-case (`add-login`) |
| `forge verify [--fast] [--json]` | Прогоняет [`verify.steps`](hooks.md#автопроверка-при-завершении-хода), записывает результат и счётчик падений; `--json` печатает `{ok, summary, failed, streak}` | 0 — прошла; 1 — упала, нет профиля или шагов; 4 — пропущена: нечем запускать шаги, нет [Git Bash](hooks.md#какая-оболочка-запускает-команды) (Windows) |
| `forge docs [--fix] [--json]` | Проверяет `AGENTS.md`/`CLAUDE.md` ([коды и уровни](agent-docs.md#коды-замечаний)); `--fix` создаёт недостающие и пустые `CLAUDE.md` со строкой `@AGENTS.md`; `--json` печатает массив `{code, level, path, message, fixable}` | 0 — ошибок нет (предупреждения допустимы); 1 — есть ошибка; 2 — неизвестный аргумент |
| `forge release --check [--json]` | Проверяет журнал и файлы версий ([коды](releases.md#проверки-журнала-изменений)); `--json` печатает массив `{code, level, path, message}` | 0 — ошибок нет (предупреждения допустимы); 1 — есть ошибка или нет раздела `release`; 2 — ошибка в использовании |
| `forge release [major\|minor\|patch\|x.y.z] [--date ГГГГ-ММ-ДД] [--json]` | [Предпросмотр](releases.md#команда-forge-release) выпуска: уровень и причина, `текущая → следующая`, файлы, тег, коммит; ничего не меняет | 0; 1 — выпускать нечего или иной отказ, либо нет раздела `release`; 2 — ошибка в использовании |
| `forge release <major\|minor\|patch\|x.y.z> --yes [--date ГГГГ-ММ-ДД] [--json]` | [Делает выпуск](releases.md#что-делает-выпуск-и-от-чего-отказывается): журнал, файлы версий, коммит `chore(release): x.y.z`, аннотированный тег; при сбое откатывает; ничего не пушит | 0; 1 — отказ или сбой (файлы возвращены); 2 — ошибка в использовании или не указан уровень |
| `forge doctor` | Node, пути плагина и проекта, [валидность профиля](profile.md#сломанный-профиль), наличие исполняемых файлов команд проверки, исключения git, [таблица маршрутизации](routing.md#переопределения-из-профиля), [настройка моделей](routing.md#проверка-настройки) (строка `Модели:`: шлюз, провайдер, отображение псевдонимов, принудительная модель субагентов и effort), [агентские файлы](agent-docs.md#команда-forge-docs), [журнал изменений](releases.md#проверки-журнала-изменений) (при разделе `release`), [Superpowers](../../README.ru.md#конфликт-с-superpowers), последние [ошибки хуков](hooks.md#fail-open-и-fail-closed) | всегда 0 |
| `forge help`, `-h`, `--help`, без аргументов | Справка | 0 |

В Windows `forge doctor` печатает ещё и строку про Git Bash — сразу после строки профиля (только в проекте с профилем): `✓ Git Bash: <путь>` или `✗ Git Bash не найден — установи Git for Windows или задай CLAUDE_CODE_GIT_BASH_PATH`. Git Bash — оболочка, которая запускает [команды профиля](hooks.md#какая-оболочка-запускает-команды); без неё проверка наличия исполняемых файлов команд пропускается, а не сообщает об их отсутствии. В macOS и Linux такой строки нет.

Если `forge verify` не может запустить шаги из-за отсутствия Git Bash, это не падение: команда печатает `SKIPPED: <шаг>: Git Bash не найден, пропущен` и сообщение про Git Bash вместо отчёта о падении, выходит с кодом 4, не трогает счётчик падений и записывает в [состояние](state.md#файл-состояния) `verify.ok: null`. С `--json` в объекте `"ok": false` и `"shell_missing": true`.

Неизвестная команда (или подкоманда `state`) — код 2, внутренняя ошибка CLI — 3. Ошибки печатаются в stderr строкой `forge: …`.

## Язык сообщений

CLI отвечает по-русски или по-английски. `FORGE_LANG=ru forge doctor` (или `en`) закрепляет язык на один запуск и важнее [`language`](profile.md#поля-профиля) из профиля; без неё CLI берёт язык из профиля, затем тот, что хук `Stop` запомнил в [`state.lang`](state.md#файл-состояния), затем системную локаль (`LC_ALL`, `LC_MESSAGES`, `LANG`), затем английский. Полный порядок — на странице [«Хуки»](hooks.md#язык-сообщений).

## Корень проекта

Корень проекта для CLI и хуков: `CLAUDE_PROJECT_DIR`, если задан; иначе ближайший предок текущего каталога с `.forge/profile.json` (не выше домашнего и не выше первого каталога с `.git` — поэтому worktree внутри основного checkout, например `.claude/worktrees/<имя>`, остаётся своим корнем); иначе корень git-репозитория; иначе текущий каталог. Если в корне linked worktree нет `.forge/profile.json`, профиль берётся из основного checkout ([Профиль в worktree](profile.md#профиль-в-worktree)), а состояние и журнал — из самого worktree.
