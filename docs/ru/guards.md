# Охрана

Два [хука `PreToolUse`](hooks.md#таблица-хуков) останавливают рискованные действия до их выполнения: охрана команд (для инструментов Bash и PowerShell: [охрана Bash](#охрана-bash) и [охрана PowerShell](#охрана-powershell)) и [охрана файлов](#охрана-файлов). Обе работают и без профиля, со встроенными значениями, на macOS, Linux и в нативном Windows.

Когда действие разрешено, охранные хуки ничего не выводят, и дальше действуют обычные разрешения Claude Code. `deny` отклоняет вызов и передаёт причину Claude, `ask` просит подтверждения у пользователя. Причины начинаются с префикса `forge:` и приходят на [языке сообщений](hooks.md#язык-сообщений); примеры на этой странице — русские:

```
forge: git push --force запрещён. Для своей ветки используй --force-with-lease.
```

## Охрана Bash

### Как читается команда

Это не полноценный разбор shell, а консервативное разбиение:

- строка делится на простые команды по `;`, `&&`, `||`, `|`, `&`, `(`, `)` и переводам строк; кавычки снимаются, комментарии и цели перенаправлений не считаются аргументами;
- перед именем команды отбрасываются присваивания (`FOO=1`), обёртки `sudo`, `doas`, `env`, `command`, `exec`, `nohup`, `time`, `nice`, `builtin`, `timeout`, `xargs`, `stdbuf`, `ionice`, `chrt`, `taskset`, `watch` и слова `if`, `then`, `else`, `elif`, `while`, `until`, `do`, `{`, `}`, `!`. Обёртка узнаётся по нормализованному имени (`/usr/bin/env`, `SUDO` и `env.exe` — тоже обёртки), её опции пропускаются вместе со значениями: `sudo -u root`, `nice -n 5`, `timeout -s KILL 10`, `env -u VAR`; ведущее позиционное слово тоже пропускается (длительность у `timeout`, приоритет у `chrt`, маска у `taskset`). Слова `if`, `then` и подобные считаются только в точном написании;
- таблицы опций обёрток не могут охватить все версии, поэтому есть страховка: если у обёртки была опция, которой нет в таблице (`sudo --made-up value git push`), а оставшееся слово — не охраняемая команда, проверка продолжается с первого более позднего слова, которое ею является (`git`, `rm`, `eval`, оболочка, `pwsh`, `powershell`, `cmd`). Лишний `ask` на `sudo --made-up echo git push` лучше молчаливого пропуска; без неизвестной опции ничего не перескакивает, и у `sudo echo git push` командой остаётся `echo`;
- `env -S 'строка'` и `watch команда…` передают строку оболочке: они читаются как `sh -c`, и строка проверяется ещё раз;
- имя команды нормализуется: последний сегмент пути (делится и по `/`, и по `\`), в нижнем регистре, без `.exe`. Поэтому `/usr/bin/git`, `git.exe`, `GIT` и `C:\Git\cmd\git.exe` — это `git`. Каталог меняет только точное имя `cd` (`/usr/bin/cd` и `CD` — нет);
- `cd <каталог>` меняет каталог для следующих команд той же строки (важно для путей `rm -r` и определения текущей ветки), `git -C <каталог>` — для этой команды;
- строка после `bash`/`sh`/`zsh`/`dash`/`ksh` с флагом `-c` проверяется как отдельная команда. `c` может стоять в любой связке коротких флагов (`-lc`, `-xc`, `-cx`), `-o`/`-O` берут значение (`-o pipefail`), `--rcfile`/`--init-file` тоже, `--` пропускается; скрипт — первый аргумент после флагов. Аргументы `eval` (без ведущего `--`) склеиваются через пробел и проверяются так же. `pwsh` и `powershell` (`-Command`) и `cmd /c`, запущенные из Bash, проверяются по [правилам PowerShell](#правила-powershell);
- команды внутри подстановок `$(…)`, `` `…` ``, `<(…)`, `>(…)` проверяются так же, где бы подстановка ни стояла: в двойных кавычках, в `${x:-$(…)}`, внутри `$((…))`, в цели перенаправления, в теле heredoc с некавыченным разделителем (`<<EOF`). Сам текст тела heredoc командой не считается;
- буквальными остаются текст в одинарных кавычках, `\$(…)` в двойных кавычках и тела heredoc с кавыченным разделителем (`<<'EOF'`, `<<"EOF"`, `<<\EOF`);
- `$'…'` декодируется (`\n`, `\t`, `\'`, `\\` и т. п.), так что `$'git' push` — это `git push`; `\x`, `\u`, `\U`, восьмеричные коды и `\c` не декодируются, слово считается зависящим от выполнения. Внутри обычных двойных кавычек `$'` — просто текст;
- `\` + перевод строки склеивается там, где его склеивает bash: `"$\⏎(…)"` — это `$(…)`. В одинарных кавычках, комментариях и телах heredoc с кавыченным разделителем строки не склеиваются;
- терминатор heredoc `<<` не снимает ведущие табуляции — только `<<-`; у нескольких heredoc в одной строке тела читаются по очереди. Внутри `$(…)` тело заканчивается и на строке `EOF)` — как в bash; строка, которая только начинается с разделителя (`EOFx`), или терминатор, который bash 3.2 и bash 5 читают по-разному, дают `ask`;
- `case`/`esac` внутри `$(…)` считаются ключевыми словами только на месте команды (`$(grep -c case f)` не путает разбор), а внутри `case` после `in` и `;;` идут шаблоны: `(esac)` или `case)` там — шаблон, а не ключевое слово. Местом команды считаются и позиции после `name()`, `function NAME`, `time -p`, `coproc`; внутри `((…))` heredoc, кавычки и комментарии не ищутся, а подстановки `$(…)` в нём проверяются;
- вложенность `bash -c`, `eval` и подстановок проверяется на три уровня; глубже — `ask` (у вложенности PowerShell [свой предел](#как-читается-команда-powershell), а когда одна оболочка запускает другую, глубина общая). Незакрытая подстановка — тоже `ask`;
- вход, который разборщик не в силах проследить (вложенность глубже примерно 32 уровней `$(` или 64 `${`, либо больше примерно 40 шагов на символ), — `ask`;
- если сама охрана упала с ошибкой — `ask` (см. [Fail-open и fail-closed](hooks.md#fail-open-и-fail-closed)).

Вердикты всех команд строки объединяются: `deny` важнее `ask`, `ask` важнее разрешения; причины победившего уровня склеиваются. `git reset --hard && git push origin main` получает `deny`.

### Правила охраны

| Команда | Вердикт | Подробности |
|---|---|---|
| `git push` в ветку из [`git.protected_branches`](#защищённые-ветки) | deny | Цель — из refspec: `main`, `HEAD:main`, `x:refs/heads/main`, `:main`, `--delete main`. `HEAD` и `@` — текущая ветка. Без refspec и без `--all` — текущая ветка. Запрещено и с `--force-with-lease` |
| `git push --force`, `-f` (и в связке флагов), `+refspec` | deny | Разрешён только `--force-with-lease` / `--force-if-includes` без `--force`, `-f` и `+refspec`, если цель не защищена. `--force` отменяет проверку аренды, поэтому `--force --force-with-lease` запрещён; `+refspec` приравнен к `--force` (консервативно) |
| `git push --mirror` | deny | |
| `git push --no-verify` | deny | |
| `git commit --no-verify`, `-n` (и в связке: `-nm "…"`) | deny | В `git commit -m -n` `-n` — текст сообщения, это разрешено |
| `git push --all`, `--branches` | ask | Отправит все локальные ветки, включая защищённые |
| `git reset --hard` | ask | |
| `rm -r`, `-R`, `--recursive` вне проекта или по непредсказуемому пути | ask | См. [Рекурсивный rm](#рекурсивный-rm); в [PowerShell](#правила-powershell) то же правило у `Remove-Item -Recurse` |
| `git push --dry-run`, `-n` | разрешено | Пробный запуск не проверяется |

Порядок проверок `git push`: `--mirror`, защищённая ветка, force, `--no-verify`, `--all`; срабатывает первое правило. Глобальные опции git перед подкомандой (`-C`, `-c`, `--git-dir`, `--work-tree`, `--namespace`, `--config-env`) пропускаются.

Типичная причина:

```
forge: push в защищённую ветку «main» запрещён (git.protected_branches). Работай в отдельной ветке и предложи пользователю PR или слияние.
```

### Сокращённые длинные опции

git принимает любой однозначный префикс длинной опции, поэтому любой префикс охраняемой опции читается как она сама: `--forc` и `--fo` — `--force`, `--no-verif` — `--no-verify`, `--mi` — `--mirror`, `--al` — `--all`, `--ha` — `--hard`. Охраняются `--force`, `--force-with-lease`, `--force-if-includes`, `--no-verify`, `--mirror`, `--all`, `--branches`, `--delete` у `push`, `--no-verify` у `commit`, `--hard` у `reset`. При неоднозначном префиксе побеждает первая опция списка (самая опасная). `--dry-run` должен быть написан полностью: сокращение не превращает команду в разрешённую.

### Рекурсивный rm

Нерекурсивный `rm` не проверяется. Для каждого пути рекурсивного удаления (здесь `rm -r`, в PowerShell — [`Remove-Item -Recurse`](#правила-powershell); правило одно):

- путь зависит от выполнения (`$VAR`, `$(…)`, обратные кавычки) — `ask`;
- путь обрезается до первого `*`, `?` или `[` и разрешается от текущего каталога (`build/*` → `build/`);
- корень файловой системы (`/`, `C:\`, UNC-корень `\\server\share\`), домашний каталог, корень проекта или его предок (`rm -rf .`, `rm -rf *` из корня) — `ask`;
- внутри проекта — разрешено;
- внутри временных каталогов, но не сам каталог, — разрешено. На macOS и Linux это `os.tmpdir()`, `/tmp`, `/private/tmp`, `/var/folders`, `/private/var/folders`; в Windows только `os.tmpdir()` (пользовательский `%TEMP%`);
- всё остальное (`../other`, `~/x`, `/etc`, `D:\data`) — `ask`.

В Windows пути читаются как пути Windows, а сравнение не различает регистр (`c:\Project\Build` лежит внутри `C:\project`). Кроме `C:\x` и `C:/x`, `~\x` — это домашний каталог. В Git Bash (инструмент Bash в Windows) `/c/x` — это `C:\x` (единственный сегмент — буква диска), а `/tmp` — временный каталог; в PowerShell таких монтирований нет, там `/c/x` — это `\c\x` на текущем диске.

### Защищённые ветки

Без профиля — `main` и `master`. Поле профиля [`git.protected_branches`](profile.md#поля-профиля) **заменяет** этот список; `[]` снимает защиту веток. Шаблоны привязаны к началу и концу имени: `*` не переходит через `/`, `**` переходит. `release/*` защищает `release/1.2`, но не `release/1.2/hotfix`.

## Охрана PowerShell

Тот же хук `pre-bash.mjs` обслуживает инструмент PowerShell в Claude Code (матчер `Bash|PowerShell`): для `tool_name: "PowerShell"` он применяет к тем же правилам — защищённые push, force, `--no-verify`, `reset --hard` и рекурсивное удаление — чтение по синтаксису PowerShell, а для всего остального — правила Bash выше. Вердикты, молчание при разрешении и fail-closed те же, что у охраны Bash.

### Как читается команда PowerShell

Снова консервативное разбиение, а не разбор PowerShell (`lib/pwsh.mjs`):

- скрипт делится на инструкции по `;`, переводам строк, `|`, `&&`, `||` и фоновому `&`; инструкции внутри групп остаются внутри. Кавычки снимаются (`'…'`, `"…"`, типографские кавычки, here-string `@'…'@` и `@"…"@`); комментарии (`#`, `<# … #>`) и цели перенаправлений аргументами не считаются. Обратная косая черта не экранирует (пути Windows остаются целыми); обратная кавычка экранирует следующий символ, а перед переводом строки продолжает строку;
- слово, значение которого известно только во время выполнения, — динамическое: переменная (`$x`, `${x}`, `$env:X`), splatting (`@args`), `$(…)`, `@(…)`, `@{…}`, `(…)`, `{…}` и `%VAR%` после `--%`. Присваивание перед командой (`$x = git push`, `$x += …`) отбрасывается, команда проверяется;
- содержимое каждой группы, блока кода и `$(…)` (в том числе внутри строки) проверяется ещё раз как отдельный скрипт там, где оно написано, выполнится оно сейчас или позже, поэтому `ForEach-Object { git push --force }` ловится;
- `&` и `.` (оператор вызова и dot-sourcing) делают следующее слово именем команды; если это переменная или группа, имя динамическое (см. [Что спрашивает и почему](#что-спрашивает-и-почему)). После `--%` остаток строки до перевода строки или `|` делится по пробелам;
- имя команды нормализуется как в Bash (`Git`, `git.exe`, `C:\Git\cmd\git.exe` — это `git`), поэтому имена нечувствительны к регистру. Параметры читаются так, как их связывает PowerShell: по полному имени, псевдониму или однозначному префиксу (`-Rec`, `-r`), без учёта регистра; значение можно приклеить двоеточием (`-Path:x`); `--` завершает параметры; длинное и среднее тире считаются тире параметра;
- `Set-Location` (`cd`, `sl`, `chdir`), `Push-Location` (`pushd`) и `Pop-Location` (`popd`) меняют каталог для следующих инструкций, как `cd` в Bash. После пути, известного только во время выполнения, без пути, после `-`, пути другого провайдера или `popd` при пустом стеке каталог неизвестен, и относительные цели удаления получают `ask`;
- скрипт, который не разбирается, получает `ask`, а не пропуск: незакрытая кавычка, скобка, here-string или блочный комментарий, закрывающая скобка без открывающей, `&` или перенаправление без продолжения, одиночный `<`, а также вход глубже или длиннее, чем следит сканер. PowerShell разбирает скрипт целиком до запуска, поэтому такой скрипт либо не выполнится, либо его нельзя прочитать статически;
- вложенность `Invoke-Expression`, `pwsh -Command`, групп и блоков кода проверяется на восемь уровней (в обычном коде блоки вложены: цикл в `if` в `ForEach-Object`); глубже — `ask`. Счётчик глубины общий с охраной Bash, поэтому одна оболочка, запускающая другую, не обойдёт предел циклом.

### Правила PowerShell

| Команда | Вердикт | Подробности |
|---|---|---|
| `git …` | как в Bash | Те же [правила](#правила-охраны): защищённая ветка, `--force`, `+refspec`, `--mirror`, `--no-verify`, `--all`, `reset --hard`; имя можно писать `GIT` или `git.exe` |
| `Remove-Item`, `del`, `erase`, `ri`, `rd`, `rmdir` (в Windows и `rm`) с `-Recurse` вне проекта или по непредсказуемому пути | ask | Цели — `-Path`, `-LiteralPath` (`-PSPath`, `-LP`) или позиционные слова; каждая проходит [правило рекурсивного удаления](#рекурсивный-rm). Считается любой префикс `-Recurse`; `-Recurse:$false`, `:0` и `:$null` выключают его. Без `-Recurse` команда не проверяется. В macOS и Linux `rm` и `rmdir` — системные программы, поэтому `rm -r` идёт по правилу Bash |
| `Remove-Item -Recurse` без цели (вход из конвейера) | ask | `Get-ChildItem … \| Remove-Item -Recurse`: неизвестно, что будет удалено |
| `Remove-Item -Recurse` на другом провайдере (`HKLM:\…`, `Registry::…`, `Env:`, `Cert:`) | ask | Любое имя диска длиннее одной буквы; `FileSystem::C:\x` — обычный путь |
| `Invoke-Expression`, `iex` с буквальной строкой | как строка | Строка проверяется как PowerShell |
| `iex` с входом из конвейера или значением, известным во время выполнения (`iex $cmd`) | ask | Прочитать нельзя |
| `pwsh`, `powershell` (и из Bash) с `-Command` / `-c` | как строка | Команда (остаток строки или первое позиционное слово) проверяется как PowerShell; параметры сопоставляются по префиксу без учёта регистра после `-`, `--` или `/` |
| `pwsh -EncodedCommand` (`-ec`), `-Command -`, значение `-Command`, известное во время выполнения | ask | Команда спрятана в base64, приходит из stdin или известна только во время выполнения |
| `pwsh -File script.ps1` | разрешено | Как запуск любого скрипта из Bash |
| `bash -c`, `sh -c`, `zsh`, `dash`, `ksh`, `eval` | как в Bash | Строка проверяется по правилам Bash |
| `cmd /c`, `/k` (и `//c` для Git Bash), где упомянуты `git`, `rm`, `bash`, `sh`, `zsh`, `wsl`, `pwsh`, `powershell`, `cmd` или `rd` / `rmdir` / `del` / `erase` с `/s` | ask | Синтаксис `cmd` охрана не разбирает. Остальное (`cmd /c dir`) разрешено; аргумент, известный во время выполнения, — `ask` |
| `Start-Process`, `saps`, `start` | как `& программа аргументы` | `-FilePath` (или первое позиционное слово) и `-ArgumentList` (или остальные позиционные слова) проверяются как вызов, так что `Start-Process git -ArgumentList push,--force` запрещён как принудительный push. Другие программы проходят; с аргументом, известным во время выполнения, охраняемая программа получает `ask` |
| команда, имя которой — переменная или группа (`& $exe …`) | ask только с опасными аргументами | См. [Что спрашивает и почему](#что-спрашивает-и-почему) |
| `Set-Alias`, `sal`, `New-Alias`, `nal` для охраняемой команды или значения, известного во время выполнения | ask | См. [Что спрашивает и почему](#что-спрашивает-и-почему) |
| `[scriptblock]::Create(…)`, `.InvokeCommand.InvokeScript(…)`, `.NewScriptBlock(…)`, `.AddScript(…)` в любом месте инструкции | ask | Скрипт, собранный из строки во время выполнения |

Вердикты всех инструкций объединяются как в Bash: `deny` важнее `ask`, `ask` важнее разрешения.

### Что спрашивает и почему

Принцип обратный «пропусти то, что не прочитал»: PowerShell разбирается целиком до запуска, поэтому скрипт, который не разбирается, прячет свой код или собирает его во время выполнения, получает `ask`. Типичные причины:

```
forge: Remove-Item -Recurse за пределами проекта или по непредсказуемому пути: HKLM:\Software\X (не путь файловой системы). Подтверди.
forge: iex выполняет код, известный только во время выполнения ($cmd), — не могу его проверить. Подтверди.
forge: -EncodedCommand прячет команду в base64 — не могу её проверить. Подтверди.
```

Исключение — **динамическое имя команды**. `& $exe push origin main` может быть чем угодно, но переменные с путями к инструментам — обычный PowerShell (`& $python script.py`, `& $msbuild /m`), и вопрос на каждую из них приучил бы нажимать «да» не глядя. Поэтому такой вызов спрашивает, только когда аргументы выглядят опасно: слово `push`, `reset` или `commit` либо флаг рекурсивного удаления (`-r`, `-rec`, `--recursive`). Причина — `forge: имя команды известно только во время выполнения ($exe), а её аргументы похожи на git push, reset, commit или рекурсивное удаление. Подтверди.`

`Set-Alias g git` позволил бы следующему `g push --force` пройти мимо проверки по имени, поэтому псевдоним для охраняемой команды (`git`, `rm`, оболочки, `pwsh`, `powershell`, `cmd`, `eval`, семейство удаления, `iex`, `Start-Process`, `Invoke-Command`) или для значения, известного во время выполнения, получает `ask`: `forge: псевдоним для «git» спрячет охраняемую команду от проверки — вызывай команду по её имени. Подтверди.`

Известные пробелы охраны PowerShell — в разделе [Ограничения](#ограничения).

## Охрана файлов

Вызов `Edit`, `Write`, `MultiEdit` или `NotebookEdit` для пути из `protected_files` отклоняется (`deny`) с причиной. Путь берётся относительно корня проекта (в Windows `\` читается как `/`); файл вне проекта сравнивается по абсолютному пути, поэтому `**/id_ed25519` ловит и `~/.ssh/id_ed25519`. Сравнение не различает регистр на любой ОС, потому что файловые системы Windows и macOS по умолчанию считают `.ENV` и `.env` одним файлом: `.ENV`, `KEY.PEM` и `Id_RSA` тоже защищены, а отрицания (`!.env.example`) не различают регистр так же.

Встроенный список действует всегда, [`protected_files`](profile.md#поля-профиля) из профиля дописывается после него:

```
.env  .env.*  .envrc  !.env.example  !.env.sample  !.env.template
**/*.pem  **/*.key  **/id_rsa  **/id_ed25519
```

### Синтаксис шаблонов

Как в `.gitignore`: шаблон без `/` совпадает на любой глубине; шаблон с `/` привязан к корню (кроме начинающихся с `**/`); `*` и `?` не переходят через `/`, `**` переходит; `{a,b}` — альтернатива; шаблон каталога покрывает всё внутри; побеждает последнее совпадение; `!шаблон` снимает защиту, в том числе встроенную (`"!.env"`). Тот же синтаксис у [`docs.watch`](agent-docs.md#что-считается-изменением).

## Ограничения

- **Охрана — страховочная сетка от ошибок, а не песочница.** Она не рассчитана на команду, которую нарочно прячут. [Не проверяется](#как-читается-команда):
  - скрипт, поданный оболочке через stdin: `… | bash`, `bash <<EOF`, `bash <<<'…'`, `bash -s`;
  - команда после обёртки не из списка (`coproc …`, `setsid …`, `unshare …`) или после неизвестной опции обёртки из списка, если позже не стоит охраняемая команда (см. страховку в разделе [Как читается команда](#как-читается-команда));
  - цель, известная только во время выполнения: `cd "$dir"`, `eval "$cmd"`, `bash -c "$script"`, `git push origin "$branch"`, refspec с недекодируемым `$'\x…'`;
  - команда, имя которой получается подстановкой: `$(true) git push --force origin main`, `${x:-}git push …`, `` `…`git push … ``, `$UNSET git push …`, `${x:-git push --force origin main}`. bash такие команды выполнит, охрана их пропустит. Пока принято так: охрана страхует от ошибок, а не от обхода;
  - `source`/`.`, алиасы и функции оболочки, `find -exec`, git-алиасы (`git -c alias.x='!…'`), скрипты, записанные в файл и запущенные (`./deploy.sh`, `npm run …`), другие интерпретаторы (`python -c`, `node -e`), `ssh`;
  - вход, который разборщик не может проследить (вложенность глубже примерно 32 уровней `$(` или 64 `${`, либо больше примерно 40 шагов на символ): целиком он не проверяется, команда получает `ask`.
- **PowerShell.** Тот же принцип «страховочная сетка, а не песочница». Не проверяется: вызовы .NET (`[IO.Directory]::Delete(…)`, `[IO.File]::Delete(…)`), `Invoke-Command -ScriptBlock $sb` и `& $sb`, где блок собран в другом месте, функции, псевдонимы и модули, определённые раньше (ловится только `Set-Alias` на охраняемую команду), скрипты, запущенные из файла (`.\deploy.ps1`, `pwsh -File`), другие интерпретаторы, `Remove-Item` без `-Recurse`, другие разрушительные командлеты (`Clear-Content`, `Format-Volume`) и git-алиасы. Динамическое имя команды с безобидными на вид аргументами проходит ([Что спрашивает и почему](#что-спрашивает-и-почему)). Запись в защищённые файлы из оболочки тоже не ловится — как и в Bash.
- `git push` без refspec проверяется по имени текущей локальной ветки. Если upstream указывает на ветку с другим именем или в `remote.<name>.push` заданы свои refspec, охрана этого не видит ([Правила охраны](#правила-охраны)).
- `--no-verify` ловится только у `git commit` и `git push`. `git -c core.hooksPath=… commit`, `git merge --no-verify` и переменные окружения, отключающие хуки, не ловятся.
- Другие разрушительные команды не охраняются: `git clean`, `git checkout -- .`, `git restore`, `git branch -D`, `find -delete`, нерекурсивный `rm`.
- [Охрана файлов](#охрана-файлов) срабатывает только на инструменты правки. Чтение `.env` не блокируется, запись через Bash (`echo … > .env`, `sed -i`) не ловится.
